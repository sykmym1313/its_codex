소요 시간은 각 서브에이전트의 `task_complete.duration_ms`를 사용했다. 시작·종료 표시는 해당 이벤트의 초 단위 타임스탬프이며, 소요 시간은 제공된 밀리초 값을 그대로 기록했다. 환경 탐색·설치·승인 대기를 포함하고, 평가자의 검증·커밋·보고서 작성·push는 제외한다. 승인 대기 시간을 분리한 순수 추론 시간은 측정 불가다.

재수정은 **수정 후 테스트 실패에 대응해 코드에 다시 변경을 가한 경우**만 센다. 환경 오류 후 PATH를 조정하거나 다시 명령을 실행한 것은 코드 재수정이 아니다. 수정 전 테스트와 평가자 검증은 재수정 및 에이전트의 수정 후 테스트 횟수에서 제외했다. 두 에이전트 모두 코드 수정 도구 호출은 1회였다.

토큰은 각 독립 실행의 마지막 `token_count.info.total_token_usage` 실측값이다. 여러 호출의 입력과 캐시 입력이 누적되므로 고유 텍스트 분량을 뜻하지 않는다. 캐시 입력은 입력 토큰의 부분집합이며 합계에 다시 더하지 않았다. 평가자 실행의 토큰은 제외했다. 실제 청구 비용 데이터는 제공되지 않아 추정하지 않았다.

## 실행 경과와 평가

### A

요구사항을 읽고 수정 전 테스트를 시도했다. 기본 PATH에 Python이 없어 번들 Python을 찾았으며, 이 Python에는 pytest가 없었다. 에이전트는 기존 `.venv` 대신 임시 폴더에 pytest 9.1.1을 설치했다. 설치 및 테스트 실행에서 권한 승격 요청이 발생하여 프롬프트의 “승인 대기 없이”는 환경 제약 때문에 달성되지 않았다.

수정 전 실제 테스트는 `1 failed, 6 passed, 2 warnings in 0.23s`였다. 이후 코드를 조사하고 조건 비교를 한 번 수정했다. 수정 후 테스트는 `7 passed, 1 warning in 0.04s`, 종료 코드 0이었다. 경고는 pytest 캐시 쓰기 권한 문제였으며 추가 코드 수정은 없었다.

에이전트 종료 후 평가자가 기존 `.venv`의 고정된 pytest 8.3.5로 다시 실행한 결과는 `7 passed in 0.06s`, 종료 코드 0이었다.

### B

요구사항과 코드를 확인하고 한 번 수정한 뒤 테스트를 시도했다. 기본 Python 명령 미인식과 번들 Python의 pytest 미설치로 2회 실행 실패했다. 이후 기존 `.venv\Scripts`를 해당 프로세스의 PATH에 추가했다. 실제 테스트가 수행된 첫 실행은 `7 passed in 0.03s`, 종료 코드 0이었다. 코드 재수정은 없었다.

에이전트 종료 후 평가자가 같은 `.venv`의 pytest 8.3.5로 다시 실행한 결과는 `7 passed in 0.02s`, 종료 코드 0이었다.

### 고정 평가 명령과 수정 범위

평가자는 저장소 루트에서 아래 명령을 사용했다. 이는 해당 가상환경에서 `python -m pytest -q`를 실행하는 것과 같다.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

공통 시작 커밋 대비 각 수정 커밋의 diff는 모두 `shipping.py`의 비교 조건 1줄 교체뿐이었다. 함수 이름과 매개변수는 유지되었다. 테스트·요구사항·pytest 설정·의존성 파일은 변경되지 않았다. 두 수정 결과의 `shipping.py` 내용도 동일하다.

버그 수정 범위 지표는 공통 시작 커밋과 **각 버그 수정 커밋** 사이에서 계산했다. 이후 A에 추가한 보고서·로그는 이 지표에 포함하지 않는다.

## 해석과 한계

두 조건은 이번 과제에서 동일한 수정과 최종 성공에 도달했고, 코드 재수정은 모두 0회였다. A는 수정 전 실패를 재현하고 수정 후 검증하는 요청된 흐름을 따랐다. B는 수정부터 진행한 뒤 실행 환경을 해결했다.

관찰된 전체 시간은 B가 짧았지만, A에는 설치·권한 승인 대기와 다른 pytest 버전 사용이 포함되었다. B의 첫 명령 실패도 코드 정답 여부와는 별개의 환경 문제였다. 따라서 전체 시간과 첫 명령 성공 여부를 전략의 효과로만 해석할 수 없다.

실행 순서는 A 다음 B로 고정되어 있고, 같은 호스트와 폴더를 사용했다. 캐시 및 A가 설치한 임시 패키지가 호스트에 남아 있어 완전한 환경 격리는 아니다. B 로그에서는 해당 임시 패키지를 사용하지 않고 기존 `.venv`를 사용한 것이 확인된다. 최종 평가는 두 결과 모두 같은 Python 3.12.14 / pytest 8.3.5 및 변경되지 않은 7개 테스트로 수행했다.

단일 경계값 버그·각 1회 실험이므로 어느 전략이 일반적으로 우월하다고 결론 내릴 수 없다. 후속 실험에서는 동일 가상환경의 Python을 시작부터 지정하고 의존성을 사전 준비하며, 실행 순서를 바꾼 반복 실험과 여러 난이도의 과제를 사용하는 것이 적절하다.
